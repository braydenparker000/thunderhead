## docs/engineering/SECURITY.md: 6.4 Fallback: client-side KDF ("server relief") **[proposal]**

If X3 fails, scrypt moves to the phone and the server does only a keyed hash. The stored verifier is **identical**, so switching between modes needs no password reset.

1. `POST /v1/auth/prelogin {username}` (public, same back-off as login) returns `{kdf: "scrypt", n, r, p, salt}`. For a wrong username it returns a deterministic fake salt `HMAC(AUTH_PEPPER, "fake-salt:" + username)[0..16]` with the same parameters, so the answer never reveals whether the username exists.
2. The page computes `dk = scrypt(NFKC(password), salt, n, r, p, 32)` in a dedicated Web Worker using a vendored WASM build (hash-wasm, MIT, pinned with SHA-256). Those pages add `'wasm-unsafe-eval'` to their CSP.
3. The page sends `{username, dk}` instead of `password`. The server computes `HMAC-SHA256(AUTH_PEPPER, dk)` and compares it with the stored verifier (~0.01 ms of CPU).
4. Setting a password: the page also checks length and blocklist, and does the breach check through the Worker (`GET /v1/auth/pwned/:prefix5`, a pass-through of the k-anonymity range API), because the server no longer sees the password.
5. A Worker variable `AUTH_KDF_WHERE = "server" | "client"` picks the mode. The server accepts only the configured field, so there's one path in production; CI tests both.

Trade-offs: `dk` is password-equivalent for this site (as the password is). Against a stolen database, an attacker still needs the pepper and then one scrypt per guess, exactly as before. Password rules move to the client, which is acceptable for a one-person app. Cost: about 0.5–2 s of phone CPU per sign-in on the owner's phone (measure at P1; target p95 ≤ 2 s).

Not fallbacks:
- The architecture review's interim "N=2^14, p=1" still costs ~37–42 ms, which doesn't fit a 10 ms budget either.
- Workers Paid ($5/month) would settle it, but costs money; ask the owner first.

## docs/engineering/SECURITY.md: 14.10 Start the account over (last resort, ask-first) **[proposal]**

For when the reset ticket can't work (for example, no mind key and no GitHub access). It wipes only `Auth`: credential, sessions, agent keys, notices and push subscriptions. Core data is untouched.
1. The owner asks in a session; the agent opens a PR adding a one-shot migration that clears the `Auth` tables when the Worker secret `AUTH_WIPE_FP` matches a fingerprint the owner made on `/setup/`.
2. The owner installs that fingerprint through GitHub (as in Open setup) and merges.
3. After deploy, `Auth` waits 24 h (same delay as a reset), then clears itself; `/setup/` opens again. Every still-signed-in device sees a red notice and can cancel during the wait.
4. Setup runs as on day one; agent keys are re-made.

## docs/engineering/PRIVACY.md: 10.2 Erase everything **[proposal]**

- Settings → Privacy → "Erase everything". The sheet asks for the password and the typed word `ERASE`.
- What goes: every `Core`, `Senses`, `Music` and `Library` table; everything in `thunderhead-private` (including backups, the events archive and the listening pass's files); all sessions except this one; all agent keys; all push subscriptions.
- What stays, said plainly on the sheet: the account itself (so the owner can still sign in); the music audio in `jarvis-music` (the system never deletes from it, by decision); Cloudflare's own logs (expire in 3–7 days); the owner's Claude session history (delete it in Claude); the old Worker until it is retired; the ported apps' own phone storage until their data moves (cleared from the phone's site settings).
- Timing: 7 days during which everything is hidden and "Cancel erase" is offered on every device; then a chunked job deletes, and the ledger keeps one line: "Everything was erased on {date}."

## docs/product/apps/MUSIC.md: 16. New feature ideas (all [proposal])

1. **"Pick up where the day left off."** At the day roll the mind notes what was playing at the end
   of the evening; the next morning, opening Music offers that album from the track after.
2. **Mood dial on a mix.** A mix's page has a 3-step dial (calmer · as is · livelier) that re-ranks
   the mix by energy from the DJ features, instantly, on the phone. Each turn is a sense, so the
   mind learns the recipe was off.
3. **Rediscovery shelf.** A Library section "Not heard in a year" built locally from stats: songs
   with ≥ 5 old plays and none in 365 days. No mind call needed.
4. **Song-length-aware queue for a time box.** "Play 25 minutes" (from the Thunderhead or the
   ··· menu) builds a queue whose durations sum to 25 min ± 30 s, ending on a track with a
   natural fade.
5. **Gentle transitions in DJ mode.** When both tracks have beat grids (from the analysis job), a
   DJ-mode crossfade of 8 s aligns downbeats; otherwise the normal crossfade.
6. **Guitar link.** A song that also exists as a tab in Guitar shows a small guitar glyph; tapping
   it opens the tab at the same position ([GUITAR](../product/apps/GUITAR.md) §12).

## docs/product/apps/GUITAR.md: 15. New feature ideas (all [proposal])

1. **Play along with the real recording.** If the piece is in the owner's Music library, attach it:
   the owner taps once on the downbeat of each section while it plays to create sync points;
   alphaTab's external-media mode then moves the cursor with the recording, slowed with
   pitch-preserving `playbackRate` (down to 50 %). Loops work on the recording too.
2. **Hard-bar finder.** From ears data, the bars with the most timing misses across the last 5
   sessions are tinted faintly in the tab, and the teacher's next plan starts there.
3. **Interleaved warm-up.** Today begins with a 5-minute warm-up that rotates three short sections
   from different songs every 90 s (interleaving research), at 80 % of best.
4. **Memory mode.** Fades the tab bar by bar for a section the owner can play cleanly at target;
   the cursor still moves, and a tap reveals the bar for 2 s. Passes in memory mode are logged
   with `focus: 'memory'`.
5. **Take-to-take compare.** Two sent takes of the same section shown as a timing strip (offset per
   note), so the owner sees rushing shrink week to week.
